## 1. 概述

### 1.1 分析目的

NewLife.Presto 的目标是成为 XCode 中 Presto 的默认 ADO.NET 驱动。本报告以用户指定的两个开源 .NET Presto 客户端为参考，回答三个问题：

1. 现有 .NET 生态已经覆盖了哪些能力，哪些是事实标准？
2. 它们的公开 Issue/PR 反映了哪些真实使用需求与兼容性风险？
3. 本项目首版应该做什么、暂缓什么、明确不做什么？

### 1.2 竞品筛选

| 代号 | 项目 | 入选理由 |
|------|------|----------|
| 参考实现 A | [nreco/presto-ado](https://github.com/nreco/presto-ado) | 面向 ADO.NET 的 Presto/Trino 适配器，与本项目定位最接近 |
| 参考实现 B | [bamcis-io/PrestoClient](https://github.com/bamcis-io/PrestoClient) | Presto REST API 客户端，协议建模与重试/取消实现较完整，是 A 的底层依赖之一 |

## 4. 值得借鉴之处

### 4.1 参考实现 A

- **薄适配层**：把 ADO.NET 表面与 REST 客户端分离，代码量小、职责清晰，便于替换底层客户端。
- **协议头切换**：用连接字符串 `TrinoHeaders` 在 Presto/Trino 之间切换，简单直接，用户无需改代码。
- **生产验证**：README 明确列出生产使用场景，说明该适配路径在实际业务中可行。
- **取消支持**：把 `CancellationToken` 贯穿到查询执行，并在读取器释放时清理底层请求。

### 4.2 参考实现 B

- **REST API 覆盖广**：除查询外还覆盖节点、线程、JMX、查询列表/详情，为运维工具提供了参考模型。
- **HTTP 重试**：指数退避 + 最大重试次数，处理瞬态错误。
- **模型层完整**：`QueryResults`、`StatementStats`、`QueryError` 等模型对协议字段建模细致，便于我们设计响应模型。
- **取消与异步**：全链路 `CancellationToken`，`Task.Delay` 替代 `Thread.Sleep`。
- **测试与 CI**：有测试工程与 CI 工作流，Issue/PR 讨论记录了真实兼容性问题。

| 参考实现 B Issue #22 | 同一状态问题在后续版本仍被反馈 | 新状态会持续出现，不能依赖枚举 | PROTO-2 + COMPAT-3 |

| 参考实现 B Issue #14/#19 | Trino 351+ 请求头重命名为 `X-Trino-*` | 双协议头必须显式支持 | COMPAT-1/COMPAT-2 |

| 参考实现 B PR #24 | 尝试增加批量拉取结果（`ExecuteQueryV1Batched`） | 大结果集应按页消费，避免一次性累积 | PROTO-4 + SQL-7 |

## 6. 差距与机会

### 6.1 本项目的目标优势

- **XCode 默认集成**：工厂、连接串、参数化、元数据、能力边界按 XCode 需求设计，而不是通用客户端 + 薄适配。
- **零第三方依赖**：只依赖 NewLife.Core，减少 JSON/HTTP 包的传递依赖与版本冲突。
- **全框架覆盖**：`net45` ~ `net11`，与 XCode 一致；新框架满足 AOT/裁剪分析。
- **类型保真**：时间类型、decimal、二进制、UUID、IP 地址与复杂类型降级策略明确。
- **协议稳健**：状态字符串化、未知字段忽略、503/Retry-After、取消 DELETE、压缩默认开启。
- **可观测**：查询 ID、错误码、SQLState、耗时与 ActivitySource。

### 6.2 需要追赶/验证的能力

| 能力 | 现状 | 计划 |
|------|------|------|
| REST 管理 API（节点/线程/JMX/查询列表） | 本项目暂缓 | 有运维工具需求时单独立项 |
| 查询结果批拉取/大结果集吞吐 | 设计为按页消费，未实测 | 核心稳定后用基准工程验证 |
| Spooling 协议 | 暂缓 | 服务端启用且有吞吐需求时评估 |
| OAuth2 / 企业 IdP | 暂缓 | 有明确接入需求时设计无交互令牌回调 |
| EF Core / EF6 | 暂缓 | 只读查询场景验证后再评估 |
| 生产使用案例 | 新项目 | 先在 XCode 内部与样例项目验证 |

### 6.3 适用场景对照

| 场景 | 更适合的选择 | 说明 |
|------|--------------|------|
| XCode ORM 访问 Presto/Trino | NewLife.Presto（目标） | 连接串、参数化、元数据、能力边界按 XCode 设计 |
| 只需要 REST 查询/管理 API | 参考实现 B 这类 REST 客户端 | 管理 API 覆盖更广，适合运维/诊断工具 |
| 已有基于参考实现 A 的 ADO 应用 | 可继续使用，或评估迁移 | 参考实现 A 的薄适配路径简单；迁移到本项目可获得零依赖、类型保真与 XCode 默认集成 |
| 需要 EF Provider | 暂不推荐本项目 | EF Provider 暂缓，且 Presto 写入/事务模型受限 |

## 8. 结论

- **市场格局**：.NET 生态已有可用的 Presto/Trino 客户端与 ADO 适配器，各有清晰定位；参考实现 A 偏 ADO 薄适配，参考实现 B 偏 REST API 客户端。
- **本项目的差异化**：不是重复造一个通用 REST 客户端，而是围绕 **XCode 默认驱动** 做深：零第三方依赖、全框架、`@` 参数、连接级元数据、类型保真、协议稳健、可观测与 AOT。
- **对第三方项目的态度**：两个项目都以 MIT 许可公开，提供了有价值的实现与真实 Issue/PR 反馈；本项目在设计中尊重并借鉴其公开经验，不贬低、不否定其适用场景。
- **首版成功标准**：XCode 能通过 `NewLife.Presto` 连接 Presto/Trino，完成查询、分页、取消与元数据读取；单元测试、假 HTTP 测试、可选真库测试与 XCode 定向测试通过。
