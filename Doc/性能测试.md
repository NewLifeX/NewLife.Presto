# Presto/Trino .NET 客户端性能对比报告

> 版本：v1.8 | 日期：2026-11-22
> 配套工程：`PerfTest/`（同一进程内串行测量，可一键复现）
> 竞品清单与功能矩阵见 [竞品分析](./竞品分析.md)

**v1.8 更新摘要**

- **认证头按令牌缓存**：JWT/显式令牌回调此前每个请求都重拼 `"Bearer " + token`，311 字符 JWT 下单次查询产生 3.90 KB 临时垃圾；改为按令牌值缓存认证头（令牌刷新时自动失效），同样方法的 A/B 降到 **0.72 KB（−82%）**。OAuth2 的 `token_type + " " + token` 一并随令牌缓存。
- **解析零碎分配**：没有列的页不再新建空 `Columns`/`Warnings` 列表，`stats.state` 复用常量实例；标量查询的解析分配 5.77 KB → **5.05 KB（−12.5%）**，无认证标量整查询 16.20 → **15.57 KB（−3.9%）**。
- 全量基准复测（Trino 476 / PrestoDB 0.300）：分配侧全部保持第一（标量 15.8/11.2 KB、扫描 0.53–0.54 MB、多列 0.94 MB，竞品 3–30 倍）；耗时侧建连、扫描、多列继续第一，标量/聚合/并发与原始 HTTP 基线互有胜负（轮间波动 30%–80%，见 §4.6 的交替 A/B）。

**v1.7 更新摘要**

- 异步路径少一层状态机：响应体读取循环并入 `ReadAsync`，异步标量 23.4 → **23.1 KB**。
- 补两组真实部署维度的验证：**百万行扫描**（本项目 557 ms / 71 MB / 峰值 55 MB，两个官方系客户端 2.3–2.5 s / 159–164 MB / 峰值 126–145 MB，三方校验和完全一致）与 **TLS**（握手被共享连接池摊薄，首连 +3.3 KB 分配、请求级开销在噪声内）。

**v1.6 更新摘要**

- **默认不再请求压缩**：实测 15000 行扫描时 gzip 解压要多花约 4–6 ms、0.5 KB，而回环/同区网络省不下等值传输时间；改由用户按网络条件显式开启 `Compression=true`。竞品默认也都不压缩，对比变为同口径。
- **终态查询不再发取消**：读取器提前关闭时，若服务端状态已是 `FINISHED`/`FAILED`/`CANCELED`，跳过后台 `DELETE`，不再做无用往返。
- 效果：扫描 18.67 → **14.64 ms**（Trino）、29.49 → **27.61 ms**（PrestoDB），多列 19.52 → 17.10 ms、33.86 → 33.61 ms；并发 213.7 → **244.2**、193.7 → 192.2 次/秒。
- 现在两个引擎上除“标量/聚合”（与原始 HTTP 基线差 0.7–0.9 ms，差在协议对象解析）外，本项目都是**全场最快**，包括快于原始 HTTP 基线。

**v1.5 更新摘要**

- **解压改由驱动自己做**：`net6+` 不再让 `HttpClient` 自动解压，改为把 gzip/deflate 流直接解到池化缓冲，省掉处理器内部的解压流与中转缓冲。
- **跨页字符串复用**：`id`/`infoUri` 每页都一样，按内容比较后复用同一个字符串实例；中间页只解析进度字段，原始 `stats` JSON 留给终页。
- 效果：标量 18.5 KB（Trino）/ **12.5 KB**（PrestoDB）、聚合 19.3/13.0 KB、建连 25.8/19.8 KB，分别比 v1.4 再降 26%–35%；PrestoDB 的标量与聚合分配已经**低于原始 HTTP 基线**。
- 单次 `SELECT 1` 的 HTTP 请求数为 5–6 个（协议本身要经历 queued→executing→完成，各客户端相同），客户端固定开销已压到每页约 2–3 KB。

**v1.4 更新摘要**

- 新增“多列类型”场景（bigint/varchar/decimal/date 四列，5000 行），补齐此前只测单列数字的盲区。
- 扁平行存储：一页数据改为连续单元格数组，不再逐行分配对象数组，扫描分配 0.95 MB → **0.50 MB**（再降 47%）。
- 文本形态的 `decimal`/`date` 直接在 UTF-8 字节上转换，省掉中间字符串：多列场景分配 1.43 MB → **0.83 MB**，PrestoDB 上这一项从落后官方客户端 5 ms 变为持平并略快。
- 基准方法升级：每个场景单独预热 + 采集前强制 GC，抑制“先测的客户端吃亏”的偏差；并发 A/B 单独复核。
- 同轮实测：Trino 建连、聚合、多列、标量均为 ADO 第一；PrestoDB 建连、多列、标量、聚合为 ADO 第一；扫描两个引擎都是 ADO 第一且只比原始 HTTP 慢 1.4–2.2 ms。
- 分配：标量 23–27 KB、扫描 0.50 MB、多列 0.83 MB、建连 30–35 KB，均为竞品的 20%–36%。

## 3. 测试方法

### 3.1 场景与 SQL

| 场景 | SQL | 测量内容 |
|------|-----|----------|
| 建立连接并首次查询 | `SELECT 1` | `new 连接 + Open + ExecuteScalar + Close`，含懒连接客户端的首次握手 |
| 标量查询 | `SELECT 1` | 复用连接执行标量查询，衡量单次往返 + 客户端解析开销 |
| 聚合 15000 行 | `SELECT count(*) FROM (扫描 SQL)` | 服务端聚合，结果只有一行 |
| 扫描 15000 行 | `SELECT x * k FROM UNNEST(sequence(1,5000)) t(x) CROSS JOIN UNNEST(sequence(1,3)) u(k)` | 逐页拉完全部数据并逐行取值 |
| 多列类型 5000 行 | `SELECT x, CAST(x AS varchar) \|\| 'abcdefghij', CAST(x AS decimal(12,2)) / 4, date_add('day', x % 300, DATE '2020-01-01') FROM UNNEST(sequence(1,5000)) t(x)` | 四列混合类型逐行取值，覆盖整数、字符串、定点数与日期 |
| 8 并发 | 同聚合 SQL | 8 条独立连接 × 5 次，统计吞吐（次/秒） |

> Trino/Presto 对 `sequence()` 有 10000 元素上限，故用 5000×3 的笛卡尔积生成 15000 行；所有客户端读取后的校验和均为 75015000（`sum(1..5000) × sum(1..3)`），多列场景为 325876593，确保比的是等价工作。

### 3.2 采样与统计

- 每个客户端先整体预热 3 次（含一次全量扫描），随后**每个场景单独再预热 3 次并强制 GC**，再进入采样：连接 10 次、标量 30 次、聚合 20 次、扫描 5 次、多列 5 次、并发 8×5。
- 整轮重复 3 次，**每个单元格取三轮均值居中那一轮的数据**；“轮间波动”=(最大均值−最小均值)/中位均值。
- 记录均值、P50、P95、最快值、每次调用的托管堆分配（`GC.GetTotalAllocatedBytes(precise: true)`）。
- NReco 默认轮询间隔（1000 ms）单次查询要 2–4 秒，放进主表会把采样时间放大数十倍，因此主表只保留 `CheckInterval=50`；默认值另用小样本单列在 §4.3。

### 3.3 公平性措施与已知偏差

公平性：同一进程、同一端点、相同 SQL、串行执行（一个客户端跑完全部场景再跑下一个），所有客户端都只做“提交查询 + 读结果”，不启用压缩以外的附加特性。

已知偏差（解读结论时需要一并考虑）：

1. **提前关闭即取消**：本项目驱动在读取器未读完时执行 `DELETE /v1/query/{id}` 释放服务端资源。自 v1.1 起该取消在读取器关闭时异步发出，不再占用调用方延迟；原始 HTTP 基线不做取消，这是设计差异，不是纯开销差异。
2. **NReco 的轮询间隔**：`CheckInterval` 默认 1000 ms，每次查询至少要等一个轮询周期。报告同时给出默认值与 `CheckInterval=50`（该包允许的最小值）两组数据。
3. **单机回环**：往返延迟只有几十微秒，客户端 CPU 开销与服务端调度占比被放大；跨机房或带 TLS 时相对差异会缩小。
4. **压缩默认值**：v1.6 起本项目默认不请求压缩（`Compression=false`），与原始 HTTP 基线和竞品同口径；广域网可显式开启。测试环境为回环，压缩与否已在 §4.6 单列对照。
5. **同步/异步通道**：本项目同步 ADO API 走 `HttpClient.Send`，异步 API 走 `SendAsync`；基准工程的 ADO 客户端均调用同步 API，因此反映的是同步通道能力。
6. **页大小不固定**：服务端按数据就绪速度返回，单页行数在 255–5000 之间浮动，因此同一 SQL 的页数在不同轮次可能不同，扫描类场景的轮间波动部分来自这里。
7. **机器复用**：被测环境同时有其它会话在使用 PrestoDB，轮间波动可达数十个百分点，因此结论以“数量级与排序是否稳定”为准，不追求小数点后精度。
8. **竞品的非常规取值**：`Trino.Ado`/`Trino.Client.ADO` 的 `GetValue` 对 `decimal` 返回自定义的 `TrinoBigDecimal`（不实现 `IConvertible`，`Convert.ToDecimal` 会抛异常），`GetDateTime` 对 `date` 列直接抛 `ArgumentException`；基准工程对这类值统一按字符串/自定义类型归一化后再比较，成本已计入其耗时。

| 4 并发 × 2 吞吐 | 1.10 次/秒 | 1.65 次/秒 |

> 该差异来自轮询策略而不是网络或服务端：把 `CheckInterval` 调到 50 ms 后单查询降到 185–284 ms（见 4.1/4.2）。生产使用建议显式设置该参数。

### 4.4 优化历程（v1.0 → v1.4，仅看数量级）

**v1.1 已完成的优化**

1. **非阻塞取消**：读取器提前关闭时，`DELETE` 在后台发出，调用方不再等待，消除短查询场景多出的一次往返。
2. **请求路径分配削减**：会话请求头按会话缓存复用；连接超时改由 `HttpClient.Timeout` 承担；SQL 不含 `@` 且无参数时跳过参数绑定扫描。

**v1.2 新增的优化**

1. **UTF-8 流式解析**：`net6+` 直接把响应字节交给 `Utf8JsonReader`，不再先变成整页字符串、也不建整页字典；`data` 行数组直接复用，数字按列类型直出（bigint→Int64、integer→Int32、double→Double）。
2. **池化响应缓冲**：`ArrayPool<Byte>` 按 `Content-Length` 预分配，增长时归还旧缓冲，解析完成即归还。
3. **统计与警告直读**：`stats` 只解析展示字段，原始 JSON 保留给 `Raw` 延迟解析；`columns`/`warnings` 直接读字段。
4. **连接串归一化只做一次**：此前每次读取属性都会重新归一化全部别名，连接建立分配 104 KB → 7 KB。
5. **取值快路径**：列类型与值类型一致时直接返回；`Int32`/`Int64` 就近转换，不再“转字符串再解析”。
6. **零碎热点**：请求头名与 `User-Agent` 缓存、Basic 认证头每语句缓存、提交 URI 缓存、分页复用执行令牌省去链接 CTS、行列表按预扫描数量精确预分配。

**v1.3 新增的优化**

1. **同步 API 真同步通道**：`ExecuteScalar`/`ExecuteNonQuery`/`ExecuteReader` 及其同步读页改用 `HttpClient.Send` + 同步流读取，不再为异步状态机付分配；异步 API 保持原实现。自定义 `HttpMessageHandler` 不支持同步时自动回退异步。
2. **`stats` 原始数据延迟解码**：从 UTF-16 字符串改为 UTF-8 字节切片，`Raw` 被访问时才解码解析，标量查询省约 3.5 KB。
3. **认证与请求对象复用**：Basic 认证头、`User-Agent`、请求头名、提交 URI、重试策略按连接/语句复用；异步请求构造少一层 Task；响应头解析去掉迭代器分配。
4. **命令执行准备合并**：同步/异步共用参数绑定、校验、超时与取消源构建。

**v1.4 新增的优化**

1. **扁平行存储**：一页数据改用一整块连续单元格数组，不再为每行分配 `Object[]`；`PrestoQueryResults.Data` 首次访问时才展开成行列表，读取器按 `行号 × 列数` 直接偏移取值。扫描 15000 行分配 0.95 MB → 0.50 MB。
2. **文本数值与日期直转**：`decimal` 列用 `Utf8Parser` 直接在 UTF-8 字节上解析、`date` 列按 `yyyy-MM-dd` 手工解析，省掉中间字符串与后续 `Decimal.Parse`/`DateTime.TryParse`；异常格式回退字符串，取值语义不变。多列场景分配 1.43 MB → 0.83 MB，PrestoDB 多列耗时 43.8 → 36.5 ms。
3. **基准方法修正**：每个场景单独预热并强制 GC，消除“先测的客户端替别人扛 JIT 与 GC”的偏差；新增多列类型场景与并发 A/B 复核。

**v1.5 新增的优化**

1. **解压自己做**：`net6+` 关闭 `HttpClient` 的自动解压，把 `Content-Encoding: gzip/deflate` 的响应直接解到池化缓冲。每页省掉处理器内部的解压流与中转缓冲约 1–2 KB，`/v1/info` 这类诊断请求也改走同一路径。
2. **跨页重复字符串复用**：`id`/`infoUri` 每页内容相同，用 `ValueTextEquals` 比较后复用上一页的实例，不再每页各分配一份。
3. **中间页只留进度统计**：`stats` 每页照常解析 `state`/`processedRows` 等进度字段，但原始 JSON 只在终页保留（`Stats.Raw`），省掉每页 0.6–1.5 KB 的切片拷贝。

**v1.6 新增的优化**

1. **默认不请求压缩**：回环/同区网络下 gzip 的解压代价（15000 行扫描约 4–6 ms）高于省下的传输时间，因此 `Compression` 默认改为 `false`，与竞品同口径；跨广域网可显式 `Compression=true`。解压实现仍保留（服务端或代理返回压缩内容时照常处理）。
2. **终态查询不再取消**：读取器提前关闭时，若服务端状态已是 `FINISHED`/`FAILED`/`CANCELED`，跳过后台 `DELETE`，少一次无用往返与相应分配。

对比基准：v1.0 为 2026-11-21 优化前同轮竞品测量，v1.2–v1.6 为 2026-11-22 不同轮次测量；**延迟受机器负载影响，分配是确定性指标，可作为主要依据**。

### 4.6 复核：并发吞吐与提前取消的开销

主表的并发数字轮间波动大，为确认“本项目是否真的在并发上落后原始 HTTP”，做两组同进程、交替执行的 A/B（Trino 476）。

**并发互相比对**（8 连接 × 10 次，交替 5 轮，单位 次/秒）

| 轮次 | 本项目（聚合 SQL） | 原始 HTTP（聚合 SQL） | 本项目（SELECT 1） | 原始 HTTP（SELECT 1） |
|-----:|------:|------:|------:|------:|
| 1 | 113.23 | 184.40 | 290.46 | 323.58 |
| 2 | 184.63 | 140.17 | 401.60 | 498.64 |
| 3 | 173.70 | 181.35 | 199.38 | 268.13 |
| 4 | 140.47 | 168.82 | 445.96 | 435.92 |
| 5 | 170.91 | 129.69 | 394.56 | 299.06 |
| **中位** | **170.91** | **168.82** | **394.56** | **323.58** |

两组都在噪声范围内互有胜负，聚合 SQL 上中位基本持平（差 1%），`SELECT 1` 上本项目更高。此前主表出现的“原始 HTTP 193 vs 本项目 166”属于单轮抖动，不是稳定的客户端差距。

**提前取消是否拖慢查询**（同一连接串行 200 次，4 轮，v1.4 时测）

| 方式 | 耗时（4 轮） | 每次分配 |
|------|-------------|---------:|
| `ExecuteScalar`（读到首行即关闭，后台 DELETE 取消） | 8.61 / 7.49 / 7.90 / 6.39 ms | 27.1–27.5 KB |
| 读完整个结果集（不触发取消） | 9.59 / 11.52 / 9.35 / 8.61 ms | 37.7–38.1 KB |
| `CommandBehavior.SingleRow` | 6.66 / 8.90 / 6.38 / 7.02 ms | 26.9–27.1 KB |

提前取消（后台 DELETE）比“读完再关”更快、分配更少：后者要多拉一次尾页，把 `stats` 与结束页的解析成本也算进调用方延迟。因此 `ExecuteScalar` 的早停策略没有为“快照干净”牺牲性能，反而更省；v1.6 起终态查询连这次 DELETE 也省掉。

**标量与原始 HTTP 基线的交替 A/B**（同一进程交替 6 轮，每轮 50 次 `SELECT 1`）

| 轮次 | 本项目 | 原始 HTTP |
|-----:|------:|---------:|
| 1 | 7.41 ms | 7.89 ms |
| 2 | 6.19 ms | 7.70 ms |
| 3 | 6.09 ms | 8.52 ms |
| 4 | 5.80 ms | 7.51 ms |
| 5 | 6.03 ms | 7.36 ms |
| 6 | 5.64 ms | 7.41 ms |
| **中位** | **6.06 ms** | **7.61 ms** |

交替测量下本项目标量比基线快约 20%：`ExecuteScalar` 读到首行就停止（终态也不再发 `DELETE`），基线则要跟到 `nextUri` 为空并额外解析终页。主表里出现过“基线 6.6 ms 快于本项目 7.5 ms”的单轮结果，属于轮内顺序与页数波动，不能作为结论。

**压缩是否划算**（15000 行扫描读完全部结果，同进程交替测量）

| 配置 | 总耗时 | 其中客户端处理（解压+解析+建对象） | 每次分配 |
|------|-------:|--------------------------------:|---------:|
| `Compression=true`（gzip） | 23.11 ms | 8.06 ms | 503 KB |
| `Compression=false` | **17.33 ms** | **3.54 ms** | 501 KB |

gzip 在回环上要多花约 4.5 ms 解压、只省下几百微秒传输，因此默认值改为不压缩；跨广域网（带宽受限）时 gzip 仍能把数百 KB 压到几十 KB，应按网络条件显式开启。

**单次 `SELECT 1` 的请求序列**（用计数处理器跟踪）

| 步骤 | 请求 | 说明 |
|------|------|------|
| 1 | `POST /v1/statement` | 提交，返回 queued 首包 |
| 2–3 | `GET …/queued/{n}` | 排队阶段轮询 |
| 4–5 | `GET …/executing/{n}` | 执行阶段轮询，数据到手 |
| 6 | `DELETE …/executing/{n}` | 读取器提前关闭，后台取消 |

一个“最简单”的查询也要 5 次同步往返加 1 次后台取消，这来自协议（queued→executing→完成）与服务端调度，不是客户端多事；所有客户端都要走同样多的往返。客户端能做的是把每次往返的固定开销压下去——这正是 v1.5 的方向（每页约 2–3 KB）。

### 4.8 异步 API 的开销

同一连接上交替测量同步与异步路径（30 次标量 / 5 次扫描，各 3 轮）：

| 路径 | 标量分配 | 扫描分配 |
|------|---------:|---------:|
| 同步 API | 16.2–16.7 KB | 489–491 KB |
| 异步 API | 23.1 KB | 551–576 KB |

异步平均多 7 KB/查询（约 40%，v1.7 合并响应体的两层异步后由 24 KB 降到 23.1 KB）。用同样的原始 HTTP 循环对照：同步 30.6–32.3 KB、异步 39.0–40.8 KB，**异步同样多 7–8.5 KB**——这部分是 `HttpClient` 异步通道（状态机、异步流读取）的固有成本，不是驱动可以省掉的。延迟两组相当。

### 4.10 TLS 与前向代理

用本地反向代理（Kestrel，同一份代码分别监听明文与自签 TLS）转发到 Trino，比较 `UseSsl` 与否：

| 场景 | 明文 | TLS | 分配 |
|------|-----:|----:|------|
| 标量查询 | 10.12 / 10.14 ms | 10.28 / 12.24 ms | +0–2 KB |
| 扫描 5000 行 | 16.72 / 21.33 ms | 17.50 / 19.31 ms | +0–1 KB |
| 新建连接 + 首查 | 9.78 / 11.03 ms | 9.73 / 11.00 ms | **+3.3 KB** |

- TLS 的主要成本是**每个端点的首次握手**（+3.3 KB 分配，回环延迟在噪声内）；`HttpClient` 按端点共享连接池，后续新建 `PrestoConnection` 不再重复握手，所以“建连+首查”与明文持平。
- 请求级加密开销在回环上不可测；广域网下带宽与往返才是主导，必要时配合 `Compression=true` 抵消 TLS 的字节放大。

### 4.11 认证头与解析的零碎分配

**Bearer 认证头缓存**（311 字符 JWT，交替 A/B，各 6 轮 × 50 次 `SELECT 1`）：

| 版本 | 无认证 | `Auth=JWT` | 认证头增量 |
|------|-------:|-----------:|-----------:|
| v1.7（每请求重拼 `"Bearer " + token`） | 16.20 KB | 20.10 KB | **+3.90 KB** |
| v1.8（按令牌值缓存） | 15.57 KB | 16.29 KB | **+0.72 KB** |

- 单次查询要发 5–6 个请求，令牌是长字符串，逐请求拼接在 311 字符令牌下就等于每查询 3.9 KB 临时垃圾；缓存后只剩 `HttpClient` 写入请求头本身的成本。
- 令牌刷新（`AccessTokenProvider` 返回新值、OAuth2 重新换取）按值比较自动失效，不会把旧头继续发出去；`PrestoOAuthTokenProvider` 的 `token_type + " " + token` 一并缓存。
- 同一轮若把令牌换掉，新令牌首请求才重建一次，其余请求继续复用。

**单页解析分配**（Trino 一次 `SELECT 1` 的 6 个真实响应体，各跑 2000 次）：

| 版本 | 解析分配/查询 | 说明 |
|------|-------------:|------|
| v1.7 | 5.77 KB | 无列的页也新建空 `Columns`/`Warnings` 列表；`stats.state` 每页新分配 |
| v1.8 | **5.05 KB** | `Columns`/`Warnings` 空时复用共享空数组；`QUEUED`/`RUNNING`/`FINISHED`/`FAILED`/`CANCELED` 复用常量 |

- 解析只占整查询的一部分：无认证标量整查询 16.20 → **15.57 KB**，解析侧的 −0.72 KB 基本就是整查询的降幅。
- 剩下的解析分配主要是每页必须物化的内容：`nextUri`（每页不同，约 250 B）、`PrestoQueryStats`、`PrestoQueryResults` 及终页保留的 `stats` 原始 JSON（供 `Stats.Raw`），没有再压缩的空间。

## 5. 结论

1. **建连、扫描、多列仍是全场最快，标量与聚合与原始 HTTP 基线互有胜负。** Trino 建连 7.79（基线 8.53）、聚合 14.38（15.99）、扫描 18.09（22.37）、多列 18.48（24.49）；PrestoDB 建连 12.93（14.42）、多列 36.20（37.11）。标量在两轮里分别是 8.42 / 6.77（Trino，基线 6.77）、13.09 / 12.53（PrestoDB），交替 A/B（§4.6）显示本项目实际不慢于基线，差异来自轮间波动。
2. **托管分配只有竞品的 8%–30%，且两个引擎的标量/聚合/并发都低于原始 HTTP 基线。** 标量 11.2–15.8 KB（竞品 97–126 KB）、聚合 12.3–16.5 KB（98–139 KB）、扫描 0.54 MB（2.39–2.98 MB）、多列 0.94 MB（4.06–4.76 MB）、建连 19–24 KB（102–160 KB）、并发 0.69–0.73 MB（3.68–6.00 MB）。千次规模压力测试（§4.7）中，本项目 0 次 Gen2 回收，两个官方系客户端各 2 次。
3. **大结果集优势最大。** 扫描 15000 行：Trino 18.09 ms（官方系 82.0–82.3 ms，快 4.5 倍）、PrestoDB 30.46 ms（官方系 37.5–44.6 ms），分配低 4.4–4.5 倍。
4. **多列混合类型仍是第一。** 4 列场景中本项目 18.5 ms（Trino）/36.2 ms（PrestoDB），原始 HTTP 基线 24.5/37.1 ms，官方系 31.0–57.4 ms，分配低 4.3–5.1 倍。
5. **并发吞吐：Trino 180.2、PrestoDB 155.3 次/秒**，两轮之间的排序在“第一—第三”之间摆动；分配始终最低（0.69–0.73 MB，竞品 3.68–6.00 MB）。
6. **认证不再放大分配**：311 字符 JWT 下的额外分配从 3.90 KB 降到 0.72 KB（§4.11），OAuth2 长期令牌同理。
7. **NReco 的默认配置不适合交互式查询**，必须显式降低 `CheckInterval`；即使调到 50 ms，仍是本组最慢（185–267 ms/次）。
8. **协议与取值兼容性更好**：两个官方系客户端默认只发 `X-Trino-*`，连 PrestoDB 需显式切换服务器类型；且它们的 `GetValue` 对 `decimal` 返回自定义的 `TrinoBigDecimal`（`Convert.ToDecimal` 直接抛异常）、`GetDateTime` 对 `date` 列抛异常。本项目统一返回标准 `Decimal`/`DateTime`/`Int64`。
9. **页大小与轮间波动需纳入解读。** 服务端单页行数在 255–5000 之间浮动，同一 SQL 的页数会变（扫描类分配的 ±10% 主要来自这里）；并发与聚合类结论以多轮 A/B 为准。

## 6. 局限与后续

- 主表为单机单节点、明文、无认证；TLS 与代理路径见 §4.10（反向代理模拟）。JWT/OAuth2 的客户端开销在 §4.11 用离线 A/B 量化（服务端未启用认证，只测客户端侧的认证头成本）。
- 多列场景覆盖 4 列（整数/字符串/定点数/日期）；更宽（>8 列）、超长字符串、`timestamp`/数组/JSON 的解析成本只做了功能验证，未做专项基准。
- 扁平行存储对单页超过 32768 个单元格的结果退回逐行数组（避免单页缓冲区过大），宽表大页场景的分配会接近 v1.3 水平。
- 结果集上限 15000 行（受 `sequence()` 限制），更大结果的吞吐需另设数据源（如 TPC-H 表）再测；单页行数不固定（255–5000），页数会随轮次变化。
- 轮间波动较大（部分单元格 20%–100%），排序在同一引擎内稳定；跨引擎横向比较只看数量级。
- **压缩默认关闭是“回环/同区最优”的选择**：实测 15000 行扫描 gzip 多花约 4.5 ms 解压、只省几百微秒传输（见 §4.6）。跨广域网、带宽受限时请显式 `Compression=true`，代价是客户端解压 CPU。解压实现保留在驱动内（服务端或代理返回压缩内容时照常处理）。
- **中间页的 `Stats.Raw` 为空**：为省掉每页的原始 JSON 拷贝，`stats` 的原始对象只在终页保留；`State`/`ProcessedRows` 等进度字段仍逐页更新，进度展示不受影响。
- 异步 API 仍比同步 API 多约 7 KB/查询（见 §4.8，实测原始 HTTP 异步同样多 7–8.5 KB，属 `HttpClient` 异步通道固有开销）；这是异步语义的成本，未用阻塞线程去换取数字。
- 流式解析只覆盖 `net6+`：`net45`/`net461`/`netstandard2.x` 仍走 JsonParser 字典路径，分配会高于本报告数字；若这些目标也需要同等分配水平，需评估引入 `System.Text.Json` 依赖。
- 待办：AOT 发布后的性能对比、>8 列宽表与超长字符串的解析成本、真实 JWT/OAuth2 服务端（本轮 TLS 用反向代理模拟，认证只在客户端侧量化）。

```powershell
# 1. 启动数据库（未安装会自动下载到空余最多的磁盘）

dotnet run --project PerfTest -c Release -- --engine trino --port 8080 --repeat 3 --exclude "（默认）" --out .tmp/性能测试-trino.md

dotnet run --project PerfTest -c Release -- --engine presto --port 8081 --repeat 3 --exclude "（默认）" --out .tmp/性能测试-presto.md

# 4. NReco 默认轮询间隔小样本（见 §4.3）
dotnet run --project PerfTest -c Release -- --engine trino --port 8080 --only "（默认）" --connect 3 --iterations 5 --aggregate 3 --scan 2 --concurrency 4 --concurrent-iterations 2

dotnet run --project PerfTest -c Release -- --probe
```
