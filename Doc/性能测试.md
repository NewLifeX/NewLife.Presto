# Presto/Trino .NET 客户端性能对比报告

> 版本：v1.1 | 日期：2026-11-21
> 配套工程：`PerfTest/`（同一进程内串行测量，可一键复现）
> 竞品清单与功能矩阵见 [竞品分析](./竞品分析.md)

**v1.1 更新摘要**

- 驱动完成两项优化：读取器提前关闭时改为非阻塞取消（少一次往返），请求头缓存 + `HttpClient.Timeout` 复用（减少每次查询分配）。
- 新增 §4.4 优化后复测：Trino 与 PrestoDB 上单次标量查询延迟下降约 60%–65%，扫描与聚合下降 30%–45%，并发吞吐接近翻倍。
- §4 的竞品对比数据保持优化前的同轮测量结果，用于公平比较；§4.4 为同机同日单独复测，仅作数量级参考。

## 1. 测试目标与范围

回答一个问题：**在同一个单机 Trino/PrestoDB 上，主流 .NET ADO.NET 客户端的开销差多少、差在哪里。**

参测客户端：

| 客户端 | 版本 | 实现路线 | 说明 |
|--------|------|----------|------|
| NewLife.Presto（本项目） | 工作区最新 | 自研 HTTP REST v1 + 零第三方依赖 | nuget 尚未发布 |
| Trino.Ado | 1.1.0 | 官方 Trino C# 客户端的持续维护分支 | 基于 Trino.Core |
| Trino.Client.ADO | 1.0.11 | 官方 Trino C# 客户端的旧版 ADO 封装 | 基于 Trino.Client |
| NReco.PrestoAdo | 1.1.0 | 薄 ADO 层 + PrestoClient（BAMCIS） | 依赖 PrestoClient 0.351.0-beta |
| 原始 HTTP v1 | — | `HttpClient` 直接调 `/v1/statement` | 协议下限基线，不含任何客户端抽象 |

| 包 | 原因 |

## 3. 测试方法

### 3.1 场景与 SQL

| 场景 | SQL | 测量内容 |
|------|-----|----------|
| 建立连接并首次查询 | `SELECT 1` | `new 连接 + Open + ExecuteScalar + Close`，含懒连接客户端的首次握手 |
| 标量查询 | `SELECT 1` | 复用连接执行标量查询，衡量单次往返 + 客户端解析开销 |
| 聚合 15000 行 | `SELECT count(*) FROM (扫描 SQL)` | 服务端聚合，结果只有一行 |
| 扫描 15000 行 | `SELECT x * k FROM UNNEST(sequence(1,5000)) t(x) CROSS JOIN UNNEST(sequence(1,3)) u(k)` | 拉完 15 页数据并逐行取值 |
| 8 并发 | 同聚合 SQL | 8 条独立连接 × 5 次，统计吞吐（次/秒） |

> Trino/Presto 对 `sequence()` 有 10000 元素上限，故用 5000×3 的笛卡尔积生成 15000 行；所有客户端读取后的校验和均为 75015000（`sum(1..5000) × sum(1..3)`），确保比的是等价工作。

### 3.2 采样与统计

- 每个客户端先预热 3 次（含一次全量扫描），再进入采样：连接 10 次、标量 30 次、聚合 20 次、扫描 5 次、并发 8×5。
- 整轮重复 3 次，**每个单元格取三轮均值居中那一轮的数据**；“轮间波动”=(最大均值−最小均值)/中位均值。
- 记录均值、P50、P95、最快值、每次调用的托管堆分配（`GC.GetTotalAllocatedBytes(precise: true)`）。

### 3.3 公平性措施与已知偏差

公平性：同一进程、同一端点、相同 SQL、串行执行（一个客户端跑完全部场景再跑下一个），所有客户端都只做“提交查询 + 读结果”，不启用压缩以外的附加特性。

已知偏差（解读结论时需要一并考虑）：

1. **提前关闭即取消**：本项目驱动在读取器未读完时执行 `DELETE /v1/query/{id}` 释放服务端资源。v1.1 起该取消在读取器关闭时异步发出，不再占用调用方延迟；§4 的数据是优化前的测量，标量与聚合因此曾比“读完即抛弃”的基线多一次往返。原始 HTTP 基线不做取消，这是设计差异，不是纯开销差异。
2. **NReco 的轮询间隔**：`CheckInterval` 默认 1000 ms，每次查询至少要等一个轮询周期。报告同时给出默认值与 `CheckInterval=50`（该包允许的最小值）两组数据。
3. **单机回环**：往返延迟只有几十微秒，客户端 CPU 开销与服务端调度占比被放大；跨机房或带 TLS 时相对差异会缩小。
4. **机器复用**：被测环境同时有其它会话在使用 PrestoDB，轮间波动可达数十个百分点，因此结论以“数量级与排序是否稳定”为准，不追求小数点后精度。

### 4.4 优化后复测（NewLife.Presto 单独复测）

优化内容：

1. **非阻塞取消**：读取器提前关闭时，`DELETE` 在后台发出，调用方不再等待，消除短查询场景多出的一次往返。
2. **分配削减**：会话请求头按会话缓存复用；连接超时改由 `HttpClient.Timeout` 承担，请求路径不再为每次请求创建超时 CTS；SQL 不含 `@` 且无参数时跳过参数绑定扫描。

复测条件与 §2 相同（同日同机、同一服务端、`--repeat 3` 取中位轮），**只运行本项目驱动**。

**读法**

- 延迟改善主要来自少一次往返：优化后标量查询接近原始 HTTP 基线，且仍保留服务端取消（异步发出）。
- 托管分配下降有限（标量约 −5%～−7%），剩余大头是 HTTP 栈与整页 JSON 字典解析；继续压缩需要改流式 JSON 解析，收益与风险需单独评估。
- 连接建立场景分配略有上升（209→236 KB / 282→322 KB），属测量波动；延迟下降来自首次查询路径的取消优化。
- 复测与 §4 不是同一轮测量，不与竞品表格直接做逐项差值；以“优化前后改善幅度”为准。

## 5. 结论

1. **同一数量级，差异主要来自往返次数与轮询策略。** 单次 `SELECT 1` 在 17–36 ms 之间（Trino），服务端调度本身就占 15–25 ms；客户端的解析与对象分配只占其中一小部分。
2. **本项目驱动的强项是大结果集。** 扫描 15000 行：Trino 上 76.4 ms 最快（比两个官方系客户端快约 20%，比原始 HTTP 只多 10 ms）；PrestoDB 上 95.8 ms 同样第一。逐页流式取数没有把整页累积成二次数据结构，是差异的主要来源。
3. **（优化前数据）在 Trino 上，标量/聚合延迟比两个官方系客户端高 5–20 ms**，与“提前关闭即 DELETE 取消查询”多一次往返相符（第 3.3 节偏差 1）；该问题已由 §4.4 的非阻塞取消解决。PrestoDB 上优化前聚合反而最快（52.4 ms）。
4. **托管分配仍偏高。** 优化前每次标量查询分配 156 KB（Trino）/245 KB（Presto），约为官方系客户端的 1.5–2.5 倍；优化后 150/237 KB，改善有限。扫描场景 5.4–5.6 MB，仍高于竞品的 2.3–2.8 MB。高分配会推高 GC 频率，是下一阶段继续治理的指标。
5. **并发吞吐处在第一梯队（优化后更进一步）。** 优化前 Trino 46.8 次/秒、Presto 48.3 次/秒；优化后复测分别为 128.9 与 95.5 次/秒。
6. **优化后短查询不再是短板。** 读取器关闭的取消改为异步发出后，`SELECT 1` 从 35.8/36.2 ms 降到 12.5/22.2 ms（Trino/PrestoDB），接近原始 HTTP 基线。
7. **NReco 的默认配置不适合交互式查询**，必须显式降低 `CheckInterval`；即使调到 50 ms，仍是本组最慢。
8. **协议兼容性**：两个官方系客户端默认只发 `X-Trino-*`，连 PrestoDB 需要显式切换服务器类型；本项目通过 `Protocol=Presto` 直接支持。

## 6. 局限与后续

- 单机单节点、无 TLS、无认证；企业网关、JWT、OAuth2、代理路径等场景未覆盖。
- 只覆盖 `BIGINT` 单列与标量结果；未测 `decimal`/`timestamp`/数组/JSON 等类型的解析成本。
- 结果集上限 15000 行（受 `sequence()` 限制），更大结果的吞吐需另设数据源（如 TPC-H 表）再测。
- 轮间波动较大（部分单元格 20%–100%），排序在同一引擎内稳定，但跨引擎横向比较只能看数量级。
- 托管分配仍高于官方系客户端：剩余大头是 HTTP 栈与整页 JSON 字典解析；下一步评估流式/按需 JSON 解析，先做可行性再动手。
- 待办：补充 TLS/认证场景、百万行扫描、GC 次数与峰值内存、AOT 发布后的对比。

## 7. 复现方式

```powershell
# 1. 启动数据库（未安装会自动下载到空余最多的磁盘）
dotnet run tools/DbCtl.cs -- start trino      # 8080
dotnet run tools/DbCtl.cs -- start presto     # 8081

# 2. 跑 Trino 对比（3 轮，输出 Markdown）
dotnet run --project PerfTest -c Release -- --engine trino --port 8080 --repeat 3 --out .tmp/性能测试-trino.md

# 3. 跑 PrestoDB 对比
dotnet run --project PerfTest -c Release -- --engine presto --port 8081 --repeat 3 --out .tmp/性能测试-presto.md

# 4. 只探测连通性 / 只跑指定客户端
dotnet run --project PerfTest -c Release -- --probe
dotnet run --project PerfTest -c Release -- --only NewLife
```
