# Presto/Trino .NET 客户端性能对比报告

> 版本：v1.2 | 日期：2026-11-22
> 配套工程：`PerfTest/`（同一进程内串行测量，可一键复现）
> 竞品清单与功能矩阵见 [竞品分析](./竞品分析.md)

**v1.2 更新摘要**

- 驱动新增 `net6+` UTF-8 流式响应解析（`Utf8JsonReader` + `ArrayPool` 池化缓冲）：不再生成整页文本与中间字典，行数据按列类型直出，`stats` 字段直读并延迟构建 `Raw`；连接串归一化改为只执行一次。
- 本版数据为 WSL 重装后的全新一轮竞品同轮测量（2026-11-22）：标量、聚合、扫描、并发全部为 ADO 客户端第一。
- 分配全面领先：标量 36–40 KB（竞品 95–101 KB）、扫描 0.97–0.98 MB（竞品 2.24–2.66 MB）、并发 1.6–1.8 MB（竞品 3.78–5.51 MB）。
- 与原始 HTTP 协议基线的差距收敛到 0–2 ms；扫描场景在 PrestoDB 上与基线持平。优化前后对比见 §4.4。

## 3. 测试方法

### 3.1 场景与 SQL

| 场景 | SQL | 测量内容 |
|------|-----|----------|
| 建立连接并首次查询 | `SELECT 1` | `new 连接 + Open + ExecuteScalar + Close`，含懒连接客户端的首次握手 |
| 标量查询 | `SELECT 1` | 复用连接执行标量查询，衡量单次往返 + 客户端解析开销 |
| 聚合 15000 行 | `SELECT count(*) FROM (扫描 SQL)` | 服务端聚合，结果只有一行 |
| 扫描 15000 行 | `SELECT x * k FROM UNNEST(sequence(1,5000)) t(x) CROSS JOIN UNNEST(sequence(1,3)) u(k)` | 逐页拉完全部数据并逐行取值 |
| 8 并发 | 同聚合 SQL | 8 条独立连接 × 5 次，统计吞吐（次/秒） |

> Trino/Presto 对 `sequence()` 有 10000 元素上限，故用 5000×3 的笛卡尔积生成 15000 行；所有客户端读取后的校验和均为 75015000（`sum(1..5000) × sum(1..3)`），确保比的是等价工作。

### 3.2 采样与统计

- 每个客户端先预热 3 次（含一次全量扫描），再进入采样：连接 10 次、标量 30 次、聚合 20 次、扫描 5 次、并发 8×5。
- 整轮重复 3 次，**每个单元格取三轮均值居中那一轮的数据**；“轮间波动”=(最大均值−最小均值)/中位均值。
- 记录均值、P50、P95、最快值、每次调用的托管堆分配（`GC.GetTotalAllocatedBytes(precise: true)`）。
- NReco 默认轮询间隔（1000 ms）单次查询要 2–4 秒，放进主表会把采样时间放大数十倍，因此主表只保留 `CheckInterval=50`；默认值另用小样本单列在 §4.3。

### 3.3 公平性措施与已知偏差

公平性：同一进程、同一端点、相同 SQL、串行执行（一个客户端跑完全部场景再跑下一个），所有客户端都只做“提交查询 + 读结果”，不启用压缩以外的附加特性。

已知偏差（解读结论时需要一并考虑）：

1. **提前关闭即取消**：本项目驱动在读取器未读完时执行 `DELETE /v1/query/{id}` 释放服务端资源。自 v1.1 起该取消在读取器关闭时异步发出，不再占用调用方延迟；原始 HTTP 基线不做取消，这是设计差异，不是纯开销差异。
2. **NReco 的轮询间隔**：`CheckInterval` 默认 1000 ms，每次查询至少要等一个轮询周期。报告同时给出默认值与 `CheckInterval=50`（该包允许的最小值）两组数据。
3. **单机回环**：往返延迟只有几十微秒，客户端 CPU 开销与服务端调度占比被放大；跨机房或带 TLS 时相对差异会缩小。
4. **机器复用**：被测环境同时有其它会话在使用 PrestoDB，轮间波动可达数十个百分点，因此结论以“数量级与排序是否稳定”为准，不追求小数点后精度。

### 4.4 优化历程（v1.0 → v1.2，仅看数量级）

**v1.1 已完成的优化**

1. **非阻塞取消**：读取器提前关闭时，`DELETE` 在后台发出，调用方不再等待，消除短查询场景多出的一次往返。
2. **请求路径分配削减**：会话请求头按会话缓存复用；连接超时改由 `HttpClient.Timeout` 承担；SQL 不含 `@` 且无参数时跳过参数绑定扫描。

**v1.2 新增的优化**

1. **UTF-8 流式解析**：`net6+` 直接把响应字节交给 `Utf8JsonReader`，不再先变成整页字符串、也不建整页字典；`data` 行数组直接复用，数字按列类型直出（bigint→Int64、integer→Int32、double→Double）。
2. **池化响应缓冲**：`ArrayPool<Byte>` 按 `Content-Length` 预分配，增长时归还旧缓冲，解析完成即归还。
3. **统计与警告直读**：`stats` 只解析展示字段，原始 JSON 保留给 `Raw` 延迟解析；`columns`/`warnings` 直接读字段。
4. **连接串归一化只做一次**：此前每次读取属性都会重新归一化全部别名，连接建立分配 104 KB → 7 KB。
5. **取值快路径**：列类型与值类型一致时直接返回；`Int32`/`Int64` 就近转换，不再“转字符串再解析”。
6. **零碎热点**：请求头名与 `User-Agent` 缓存、Basic 认证头每语句缓存、提交 URI 缓存、分页复用执行令牌省去链接 CTS、行列表按预扫描数量精确预分配。

对比基准：v1.0 为 2026-11-21 优化前同轮竞品测量，v1.2 为 2026-11-22 本轮测量；两次测量之间重装过 WSL、机器负载不同，**延迟只看数量级，分配是确定性指标，可作为主要依据**。

**读法**

- 分配是本次的主战场：标量 −72%～−85%，扫描 −81%～−83%，连接建立 −78%～−84%；原因都在解析与连接串归一化，不依赖服务端状态。
- 扫描延迟从 76/96 ms 降到 36/35 ms，主要来自不再构造整页字典与逐单元格复制；与原始 HTTP 基线持平或仅差 1–2 ms。
- 并发吞吐 v1.2 的数字低于 v1.1 复测，但同轮原始 HTTP 基线也从 53 次/秒升到 126 次/秒，说明是服务端/机器状态差异，不是回退。

## 5. 结论

1. **全部 ADO 场景第一。** 本轮同轮测量中，本项目的建连、标量、聚合、扫描与 8 并发吞吐均为 ADO 客户端第一；与原始 HTTP 协议基线的差距只剩 0–2 ms。
2. **托管分配全面领先。** 标量 36–40 KB（竞品 95–101 KB）、扫描 0.97–0.98 MB（竞品 2.24–2.66 MB）、并发 1.6–1.8 MB（竞品 3.8–5.6 MB）。高分配会推高 GC 频率，这一项直接决定高并发下的稳定性。
3. **大结果集优势最大。** 扫描 15000 行：Trino 上 36.0 ms，比两个官方系客户端快 1.8–2.3 倍，分配只有它们的 37%–42%；PrestoDB 上 35.3 ms 与原始 HTTP 持平，分配只有竞品的 37%–41%。
4. **短查询不再是短板。** `SELECT 1` 为 11.5/14.3 ms（Trino/PrestoDB），与原始 HTTP 基线相差 1.2/1.6 ms；非阻塞取消保留了服务端资源释放能力。
5. **连接建立最快且分配最低。** Trino 13.9 ms / 47 KB、PrestoDB 14.6 ms / 44 KB；竞品为 15.4–22.5 ms / 97–121 KB。连接串归一化只执行一次是关键。
6. **并发吞吐第一。** Trino 102.6 次/秒、PrestoDB 140.3 次/秒，均为 ADO 第一；原始 HTTP 基线仍更高，因为它省掉了全部 ADO 表面与协议状态。
7. **NReco 的默认配置不适合交互式查询**，必须显式降低 `CheckInterval`；即使调到 50 ms，仍是本组最慢。
8. **协议兼容性**：两个官方系客户端默认只发 `X-Trino-*`，连 PrestoDB 需要显式切换服务器类型；本项目通过 `Protocol=Presto` 直接支持。

## 6. 局限与后续

- 单机单节点、无 TLS、无认证；企业网关、JWT、OAuth2、代理路径等场景未覆盖。
- 主表以 `BIGINT` 单列与标量结果为主；`decimal`/`timestamp`/数组/JSON 的解析成本只做了功能验证，未做专项基准。
- 结果集上限 15000 行（受 `sequence()` 限制），更大结果的吞吐需另设数据源（如 TPC-H 表）再测。
- 轮间波动较大（部分单元格 20%–100%），排序在同一引擎内稳定；跨引擎横向比较只看数量级。
- 流式解析只覆盖 `net6+`：`net45`/`net461`/`netstandard2.x` 仍走 JsonParser 字典路径，分配会高于本报告数字；若这些目标也需要同等分配水平，需评估引入 `System.Text.Json` 依赖。
- 待办：补充 TLS/认证场景、百万行扫描、GC 次数与峰值内存、AOT 发布后的对比、压缩开关（gzip）对 CPU 与带宽的量化。

