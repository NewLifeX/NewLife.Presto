# Presto/Trino .NET 客户端性能对比报告

> 版本：v1.3 | 日期：2026-11-22
> 配套工程：`PerfTest/`（同一进程内串行测量，可一键复现）
> 竞品清单与功能矩阵见 [竞品分析](./竞品分析.md)

**v1.3 更新摘要**

- 同步 ADO API 改为真同步通道（`HttpClient.Send` + 同步流读取），不再为异步状态机付分配；异步 API 保持原实现，自定义 handler 不支持同步时自动回退。
- 其余削减：`stats` 原始数据改为 UTF-8 字节按需解码；认证头、请求头名、提交 URI、重试策略按连接/语句复用；异步请求构造少一层 Task；响应头解析去掉迭代器分配。
- 同轮实测：Trino 与 PrestoDB 的建连、标量、聚合、扫描全部为 ADO 第一；并发吞吐经 5 轮 A/B 确认为第一（Trino 176.5 vs 155.1 次/秒、PrestoDB 146.2 vs 130.3 次/秒）。
- 分配：标量 23–28 KB（竞品 96–105 KB）、扫描 0.95 MB（竞品 2.27–2.71 MB）、建连 30–35 KB（竞品 96–120 KB）。
- 与原始 HTTP 基线的差距：标量/聚合/建连已反超；扫描 Trino 落后 0.6 ms、PrestoDB 领先 8.5 ms；并发吞吐落后基线 0–21%。

回答一个问题：**在同一个单机 Trino/PrestoDB 上，主流 .NET ADO.NET 客户端的开销差多少、差在哪里。**

## 3. 测试方法

### 3.1 场景与 SQL

| 场景 | SQL | 测量内容 |
|------|-----|----------|
| 建立连接并首次查询 | `SELECT 1` | `new 连接 + Open + ExecuteScalar + Close`，含懒连接客户端的首次握手 |
| 标量查询 | `SELECT 1` | 复用连接执行标量查询，衡量单次往返 + 客户端解析开销 |
| 聚合 15000 行 | `SELECT count(*) FROM (扫描 SQL)` | 服务端聚合，结果只有一行 |
| 扫描 15000 行 | `SELECT x * k FROM UNNEST(sequence(1,5000)) t(x) CROSS JOIN UNNEST(sequence(1,3)) u(k)` | 逐页拉完全部数据并逐行取值 |
| 8 并发 | 同聚合 SQL | 8 条独立连接 × 5 次，统计吞吐（次/秒） |

> Trino/Presto 对 `sequence()` 有 10000 元素上限，故用 5000×3 的笛卡尔积生成 15000 行；所有客户端读取后的校验和均为 75015000（`sum(1..5000) × sum(1..3)`），确保比的是等价工作。

### 3.2 采样与统计

- 每个客户端先预热 3 次（含一次全量扫描），再进入采样：连接 10 次、标量 30 次、聚合 20 次、扫描 5 次、并发 8×5。
- 整轮重复 3 次，**每个单元格取三轮均值居中那一轮的数据**；“轮间波动”=(最大均值−最小均值)/中位均值。
- 记录均值、P50、P95、最快值、每次调用的托管堆分配（`GC.GetTotalAllocatedBytes(precise: true)`）。
- NReco 默认轮询间隔（1000 ms）单次查询要 2–4 秒，放进主表会把采样时间放大数十倍，因此主表只保留 `CheckInterval=50`；默认值另用小样本单列在 §4.3。

### 3.3 公平性措施与已知偏差

公平性：同一进程、同一端点、相同 SQL、串行执行（一个客户端跑完全部场景再跑下一个），所有客户端都只做“提交查询 + 读结果”，不启用压缩以外的附加特性。

已知偏差（解读结论时需要一并考虑）：

1. **提前关闭即取消**：本项目驱动在读取器未读完时执行 `DELETE /v1/query/{id}` 释放服务端资源。自 v1.1 起该取消在读取器关闭时异步发出，不再占用调用方延迟；原始 HTTP 基线不做取消，这是设计差异，不是纯开销差异。
2. **NReco 的轮询间隔**：`CheckInterval` 默认 1000 ms，每次查询至少要等一个轮询周期。报告同时给出默认值与 `CheckInterval=50`（该包允许的最小值）两组数据。
3. **单机回环**：往返延迟只有几十微秒，客户端 CPU 开销与服务端调度占比被放大；跨机房或带 TLS 时相对差异会缩小。
4. **压缩默认值**：本项目 `Compression` 默认开启（gzip），原始 HTTP 基线与部分竞品未启用；本机回环下这部分带来约 8 KB/查询的分配与 1–2 ms 延迟，广域网则相反。对比时需把该差异计入。
5. **同步/异步通道**：本项目同步 ADO API 走 `HttpClient.Send`，异步 API 走 `SendAsync`；基准工程的 ADO 客户端均调用同步 API，因此反映的是同步通道能力。
4. **机器复用**：被测环境同时有其它会话在使用 PrestoDB，轮间波动可达数十个百分点，因此结论以“数量级与排序是否稳定”为准，不追求小数点后精度。

### 4.4 优化历程（v1.0 → v1.2，仅看数量级）

**v1.1 已完成的优化**

1. **非阻塞取消**：读取器提前关闭时，`DELETE` 在后台发出，调用方不再等待，消除短查询场景多出的一次往返。
2. **请求路径分配削减**：会话请求头按会话缓存复用；连接超时改由 `HttpClient.Timeout` 承担；SQL 不含 `@` 且无参数时跳过参数绑定扫描。

**v1.2 新增的优化**

1. **UTF-8 流式解析**：`net6+` 直接把响应字节交给 `Utf8JsonReader`，不再先变成整页字符串、也不建整页字典；`data` 行数组直接复用，数字按列类型直出（bigint→Int64、integer→Int32、double→Double）。
2. **池化响应缓冲**：`ArrayPool<Byte>` 按 `Content-Length` 预分配，增长时归还旧缓冲，解析完成即归还。
3. **统计与警告直读**：`stats` 只解析展示字段，原始 JSON 保留给 `Raw` 延迟解析；`columns`/`warnings` 直接读字段。
4. **连接串归一化只做一次**：此前每次读取属性都会重新归一化全部别名，连接建立分配 104 KB → 7 KB。
5. **取值快路径**：列类型与值类型一致时直接返回；`Int32`/`Int64` 就近转换，不再“转字符串再解析”。
6. **零碎热点**：请求头名与 `User-Agent` 缓存、Basic 认证头每语句缓存、提交 URI 缓存、分页复用执行令牌省去链接 CTS、行列表按预扫描数量精确预分配。

**v1.3 新增的优化**

1. **同步 API 真同步通道**：`ExecuteScalar`/`ExecuteNonQuery`/`ExecuteReader` 及其同步读页改用 `HttpClient.Send` + 同步流读取，不再为异步状态机付分配；异步 API 保持原实现。自定义 `HttpMessageHandler` 不支持同步时自动回退异步。
2. **`stats` 原始数据延迟解码**：从 UTF-16 字符串改为 UTF-8 字节切片，`Raw` 被访问时才解码解析，标量查询省约 3.5 KB。
3. **认证与请求对象复用**：Basic 认证头、`User-Agent`、请求头名、提交 URI、重试策略按连接/语句复用；异步请求构造少一层 Task；响应头解析去掉迭代器分配。
4. **命令执行准备合并**：同步/异步共用参数绑定、校验、超时与取消源构建。

对比基准：v1.0 为 2026-11-21 优化前同轮竞品测量，v1.2/v1.3 为 2026-11-22 不同轮次测量；**延迟受机器负载影响，分配是确定性指标，可作为主要依据**。

## 5. 结论

1. **全部 ADO 场景第一。** 建连、标量、聚合、扫描均为 ADO 客户端第一；并发吞吐单独用 5 轮 A/B 复核同样第一（Trino 176.5 vs 155.1 次/秒，PrestoDB 146.2 vs 130.3 次/秒）。
2. **托管分配全面领先。** 标量 23–28 KB（竞品 96–105 KB）、扫描 0.95 MB（竞品 2.27–2.71 MB）、建连 31–35 KB（竞品 96–120 KB）、并发 1.25–1.28 MB（竞品 3.75–5.50 MB）。高分配会推高 GC 频率，这一项直接决定高并发下的稳定性。
3. **大结果集优势最大。** 扫描 15000 行：Trino 22.8 ms，比两个官方系客户端快 3.0–3.4 倍；PrestoDB 30.9 ms，快 1.5–1.9 倍。分配只有竞品的 35%–42%。
4. **短查询已与协议基线平起平坐甚至更快。** `SELECT 1` 为 7.03/13.02 ms（Trino/PrestoDB），同轮原始 HTTP 为 7.60/13.25 ms；快照仍保留非阻塞取消，未用“少一次往返”换数字。
5. **连接建立最快且分配最低。** Trino 7.0 ms / 35 KB、PrestoDB 13.2 ms / 31 KB；竞品为 9.4–16.5 ms / 96–120 KB。
6. **并发吞吐第一梯队。** 全量轮次中 Trino 166.4、PrestoDB 166.4 次/秒；原始 HTTP 基线与个别竞品的单轮数字会更高（服务端调度波动），但 5 轮 A/B 下本项目稳定领先 ADO 竞品。原始 HTTP 仍略高，因为它省掉了全部 ADO 表面与结果对象。
7. **NReco 的默认配置不适合交互式查询**，必须显式降低 `CheckInterval`；即使调到 50 ms，仍是本组最慢。
8. **协议兼容性**：两个官方系客户端默认只发 `X-Trino-*`，连 PrestoDB 需要显式切换服务器类型；本项目通过 `Protocol=Presto` 直接支持。

## 6. 局限与后续

- 单机单节点、无 TLS、无认证；企业网关、JWT、OAuth2、代理路径等场景未覆盖。
- 主表以 `BIGINT` 单列与标量结果为主；`decimal`/`timestamp`/数组/JSON 的解析成本只做了功能验证，未做专项基准。
- 结果集上限 15000 行（受 `sequence()` 限制），更大结果的吞吐需另设数据源（如 TPC-H 表）再测。
- 轮间波动较大（部分单元格 20%–100%），排序在同一引擎内稳定；跨引擎横向比较只看数量级。
- **gzip 默认开启是带宽与 CPU 的取舍**：本机回环下，`Compression=true` 比 `false` 每次标量多约 8 KB 分配、多 1–2 ms；广域网下 gzip 通常能显著减少传输时间。追求最低延迟/分配可在连接串设置 `Compression=false`。
- 异步 API 仍比同步 API 多约 8 KB/查询（HttpClient 异步通道固有开销）；这是异步语义的成本，未用阻塞线程去换取数字。
- 流式解析只覆盖 `net6+`：`net45`/`net461`/`netstandard2.x` 仍走 JsonParser 字典路径，分配会高于本报告数字；若这些目标也需要同等分配水平，需评估引入 `System.Text.Json` 依赖。
- 待办：补充 TLS/认证场景、百万行扫描、GC 次数与峰值内存、AOT 发布后的对比、不同结果宽度（多列/字符串）的解析成本。

## 7. 复现方式

```powershell
# 1. 启动数据库（未安装会自动下载到空余最多的磁盘）
dotnet run tools/DbCtl.cs -- start trino      # 8080
dotnet run tools/DbCtl.cs -- start presto     # 8081

# 2. 跑 Trino 对比（3 轮，排除慢速的 NReco 默认配置）
dotnet run --project PerfTest -c Release -- --engine trino --port 8080 --repeat 3 --exclude "（默认）" --out .tmp/性能测试-trino.md

# 3. 跑 PrestoDB 对比
dotnet run --project PerfTest -c Release -- --engine presto --port 8081 --repeat 3 --exclude "（默认）" --out .tmp/性能测试-presto.md

# 4. NReco 默认轮询间隔小样本（见 §4.3）
dotnet run --project PerfTest -c Release -- --engine trino --port 8080 --only "（默认）" --connect 3 --iterations 5 --aggregate 3 --scan 2 --concurrency 4 --concurrent-iterations 2

# 5. 只探测连通性 / 只跑指定客户端
dotnet run --project PerfTest -c Release -- --probe
dotnet run --project PerfTest -c Release -- --only NewLife
```
